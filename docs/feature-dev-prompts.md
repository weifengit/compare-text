## 开发顺序与依赖（开工前先读这一节）

### 最终目标

两套并行的工作方式，共用同一套对比内核（`src/compute.js`）：

- **少量文件** → 用现有的 UI 页面直观看差异（**已实现，不需要开发**）
- **文件多 / 不想看 UI** → 通过和 deepseek harness（dsh）对话描述怎么对比，由应用生成**自包含 HTML 对比报告**供人查看

### 提示词之间的关系

| 提示词                         | 状态                         | 说明                                                                                                                                  |
| ------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 提示词 1（WASM OCR）        | **已实现**             | 内置 onnxruntime-web + PP-OCRv4（无 Python）；交互弹窗 + 无头报告自动识别双路径，见 `src/ocr.js`/`src/ocr-worker.js` |
| 提示词 2（云端大模型语义识别） | ⛔**已作废，不要实施** | 接上 dsh 后整块由 harness 承担（dsh 自带 LLM + 工具调用）。应用侧**不再**需要 API Key 配置界面、厂商兼容、prompt 编排、结果渲染 |
| 提示词 3（对比结果导出）       | 部分并入提示词 4             | 其中的**报告模板 `src/report.js` 与提示词 4 共用**；"人在页面里点导出"这一入口可延后                                          |
| 提示词 4（无头渲染通道）       | **主线核心**           | 一切的承重墙，先做                                                                                                                    |
| 提示词 5（dsh 插件对接）       | 最后做                       | 依赖提示词 4 的`tools/render.js` 已稳定                                                                                             |

### 推荐开发顺序

按阶段推进，**每个阶段结束都应是一个可验证的完整状态**，不要跨阶段并行。

  验收：`npm test` / `npm run test:all` 全绿，界面行为完全不变。

#### 阶段 B：最小可用闭环（一条命令出一份单对报告）

  **这一步没过就不要往下做**，否则报告模板要返工。
- **B2. `src/report.js` 报告模板**（提示词 4 第 5 项）
  先**只做左右分栏视图**，跳过 Redline 与批量总览，够跑通闭环即可。
  自包含单文件、CSS/JS/图片全内联、接收方零安装双击即看。
- **B3. `tools/render.js` 无头任务入口**（提示词 4 第 2、3 项）
  起临时静态服务 + headless Edge + CDP 驱动页面。**从 `tools/spike-capture.js` 起步**，它已有 CDP 连接、超时、看门狗、逐页滚动收敛等基础设施，不要从零重写。
- **B4. 逐页快照采集接入**（提示词 4 第 4 项）
  照抄 spike 里已验证的做法，并逐条落实"已知的坑"一节的 6 条措施。
- **阶段 B 完成标志**：`node tools/render.js --task demo.json` 在无人工介入下产出一份单对报告，在**未安装本应用**的电脑上双击打开，4 区块完整、颜色标注与页面所见一致、快照放大后清晰。

#### 阶段 C：批量与双视图（提示词 3 的 ②③）

- **C1.** 批量总览（每对一行：文件名、差异数、锚点超链接）
- **C2.** Redline 合并视图（红删除线 + 蓝下划线），与分栏视图报告内一键切换

#### 阶段 D：对接 dsh（提示词 5）

- 插件壳（自定义命令 / skill）+ 任务 JSON schema 与范例 + 自然语言→任务 JSON 的提示词
- 依赖：阶段 B/C 的 `tools/render.js` 已稳定

#### 阶段 E：可选 / 独立

- **E1. 扫描版 PDF 的 OCR**（**已实现**）：内置 WASM OCR（onnxruntime-web + PP-OCRv4），无 Python；验收见提示词 1
- **E2. 桌面（Tauri）模式的无头渲染**（提示词 4 文末"后续扩展"）：两条路，优先考虑让 WebView2 开放调试端口以复用同一套 CDP 驱动代码

### 交给 AI 开发时的注意事项

1. **一次只做一个阶段**，把该阶段对应的提示词章节 + 本节一起给它。
2. **明确告知它提示词 2 已作废**，避免它去实现云端大模型 API 配置那一整块。
3. **让它先读 `tools/spike-capture.js` 的文件头**——验证结论、实测数据、5 条坑及其对应代码位置都写在那里。
4. 每个阶段结束时要求它跑 `npm test` / `npm run test:all`，确保既有功能不回归。

## 提示词 1：扫描版 PDF 的 OCR 识别（内置 WASM OCR，无 Python）

### 项目背景

这是一个 Tauri 2 + 纯前端（无框架，原生 JS）的离线文本对比工具。仓库结构：

- 前端入口 `index.html`，逻辑在 `src/` 下按模块拆分（`app.js`、`pipeline.js`、`pdfview.js`、`compute.js`、`ocr.js` 等）
- PDF 渲染与文本提取用 pdf.js（`lib/pdf.min.js`），文本提取在 `src/pdfview.js` 的 `extractPanel`（基于 `getTextContent`，**只能提取文字版 PDF，扫描件提取结果为空**）
- 无头报告通道 `tools/render.js`（headless Edge + CDP，驱动同一套 `src/` 模块）
- 当前 CSP（`src-tauri/tauri.conf.json`）：`connect-src 'self' blob: ipc:`（OCR 资源同源 fetch，无需改）

### 需求

为扫描版（无文字层）PDF 增加 OCR 识别能力，使这类文件也能参与文本对比与报告生成。

**已选定的技术路线：应用内置 WASM OCR（onnxruntime-web 1.30 + PP-OCRv4 中文模型）。**
不依赖 Python / 系统运行时 / 网络：onnx 模型在浏览器/WebView 里用 WebAssembly 推理，全程离线。
打包增量约 **29MB**（`lib/onnxruntime/` 13.6MB + `models/` 15.5MB，均已 vendored 进仓库并被 `serve.js build` 复制进 `dist/`）。

### 具体要求

1. **检测与确认（交互模式）**

   - 加载 PDF 时先走现有 `extractPanel`，若提取结果为空/极少且页数 > 0，判定为扫描件
   - 弹确认框「检测到扫描版 PDF（无文字层），是否启用本地 OCR 识别？」，**用户确认后才跑**，不默认自动跑；含「跳过」入口
   - 首次识别需加载模型（约 15MB，之后复用同一运行时，单例缓存）；加载/逐页识别都有进度提示，可取消（取消后状态干净）
2. **WASM OCR 引擎（src/ocr.js，UMD 三端复用：浏览器 / Web Worker / Node 测试）**

   - 引擎：PP-OCRv4 det + cls + rec（SWHL ONNX 导出，RGB 通道顺序），CTC 解码 + `models/ppocr_keys_v1.txt` 字典（index 0 = blank）
   - 识别结果含**行级坐标**（det 文本框）→ 经 `linesToTextItems` 转成与 pdf.js `collectItems` **同构**的 textItems（`{transform,width,line,col,str,hasEOL}`）
   - 差异标注直接画在扫描页上（复用 `computeHlBoxes` 坐标映射，零改动），**不需要**生成文字版 PDF
   - Worker 封装 `src/ocr-worker.js`（classic Worker，`importScripts` 加载 ort + ocr.js；图片用 transferable 传输；`wasmPaths` 显式给绝对 URL 解决 classic Worker 动态 import 相对路径解析问题）
3. **与对比流程的集成（src/pipeline.js + src/pdfview.js）**

   - `pipeline.js` 检测扫描件 → `onScannedPdf(side)` 回调 → `runOcr(side)` 逐页识别（`PdfView.renderPageToImage` 离屏渲染 → worker 推理 → 累积 text + items），`setOcrResult` 注入面板，`onPanelText` 进编辑区
   - 行号跨页连续（`linesToTextItems` 的 `startLine` 参数），OCR 文本与 textItems 行号一一对应
   - 换文件/切 tab/取消都会作废在途 OCR（`ocrSeq` 令牌）
4. **无头报告通道（tools/render.js）**

   - 加载侧前设 `window.__HEADLESS_OCR__ = true`：扫描件**自动识别**，不弹窗，报告流程不中断
   - 识别结果作为该侧文本进对比；快照仍按页截扫描件（OCR 标注后的页面）
   - 与交互模式共享同一 `src/ocr.js` 代码路径（报告工具不重新实现 OCR）
5. **DSH 插件生态（可选增强，未强制）**

   - 检测到扫描件时，在 DSH 集成模式下可提醒用户安装社区 OCR 插件
     （`dsh-md-convert`、`dsh-ocr-local`、`dsh-pdf` 等），用插件输出做报告/对比，与本应用内置 WASM OCR 互为补充
   - 报告流程 `tools/report.js` 保持接受调用方预置的 OCR 文本（兼容插件侧提取）

### 约束

- 应用本体打包体积增量控制在 ~30MB 内（onnx 模型 + ort 运行时，不引入任何 Python 解释器）
- 保持离线：OCR 全程本地（WASM 推理），不允许任何网络请求；`lib/onnxruntime/` 与 `models/` 必须提交进仓库、被 `serve.js build` 复制
- 遵循项目 CLAUDE.md：最小改动、匹配现有代码风格、OCR 逻辑独立成模块（`src/ocr.js` + `src/ocr-worker.js`），不堆进 `pdfview.js`
- 交互与无头（报告）模式必须共享同一 OCR 路径，不允许两份实现

### 验收标准

- `node test/ocr.js`：8 项单元 + 真实推理全绿（识别出样例图「去污」「国标」等关键词）
- `node test/e2e-ocr.js`：浏览器端到端 12 项全绿（扫描件弹窗 → 确认 → 识别文本进编辑区 → **扫描页出现差异标注** → 文字版 PDF 不弹窗）
- 无头通道：`render.js` 处理含扫描版 PDF 的任务自动识别，报告含两侧快照、无 OCR 失败 warning
- `npm test` 全绿；交互模式取消 OCR 后状态干净

## 提示词 2：文本差异语义识别（云端大模型 API）

> ⛔ **本提示词已作废，不要实施。**
> 原因：本项目已确定走 deepseek harness（dsh）插件的路线。dsh 本身就是"LLM + 工具调用循环"，
> 语义分析由 dsh 直接阅读报告中的差异统计与差异片段完成。**应用侧不再需要** API Key 配置界面、
> 厂商兼容、prompt 编排与结果渲染，也不需要调整 CSP。
> 以下内容仅作历史记录保留，实现提示词 4 / 提示词 5 时请忽略本节的"具体要求"。

### 项目背景

同提示词 1 的"项目背景"。补充：差异计算在前端 `src/compute.js` 完成（基于 `lib/diff.min.js`），产出结构化的行级差异（新增/删除/修改），UI 上有"折叠相同行""仅看差异"等过滤能力（`src/filterbar.js`）。

### 需求

在现有字符级差异的基础上，增加**语义级分析**：判断这批文字差异对文档上下文语义的影响程度，给出"影响大 / 中 / 小"的结论与简要理由。

**已选定的技术路线：调用云端大模型 API，用户自行配置厂商与 API Key。** 不引入本地模型。

### 具体要求

1. **配置**

   - 设置界面：API Base URL、API Key、模型名，默认兼容 OpenAI 格式的 `/chat/completions`（这样 OpenAI、DeepSeek、通义、Kimi 等主流厂商都能接）；Key 本地安全存储（Tauri 侧存系统 keychain 或至少不明文落盘到仓库目录），永不回传除用户所配厂商之外的任何地址
   - 提供"测试连接"按钮验证配置可用
2. **分析流程**

   - 输入：从现有差异结果中提取**差异片段 + 必要的上下文窗口**（差异前后各若干行），不是整篇文档无脑发送；差异很多时分批/汇总，控制 token 消耗
   - 输出（要求模型返回结构化 JSON，程序解析而非展示原始文本）：整体影响等级（大/中/小）、一句话结论、以及逐处差异的简要说明（可选，按 token 预算取舍）
   - 结果展示在差异区域顶部/侧边，与现有 UI 风格一致
3. **隐私与降级**

   - 首次使用该功能时明确提示：差异内容将发送至用户配置的第三方 API
   - 未配置 API、网络失败、额度不足时，应用其他功能完全不受影响，该功能单独给出错误提示
4. **CSP 调整**：`tauri.conf.json` 的 `connect-src` 需放开到允许用户配置的 API 域名（实现时评估：按用户配置动态注入，或放宽为 `https:` 并在文档中说明安全影响）

### 约束

- 不引入前端框架/重型 SDK，直接 `fetch` 调 OpenAI 兼容接口
- 除该功能外应用保持离线可用
- 遵循项目 CLAUDE.md：最小改动、LLM 调用与结果渲染逻辑独立成模块文件

### 验收标准

- 配置有效 Key 后：对一份有实质语义变化（如合同金额、责任条款改动）的对比，结论判"影响大"并给出理由；对仅措辞微调的对比，判"影响小"
- 未配置/断网时：功能入口提示明确，其余功能正常

## 提示词 3：批量对比结果导出（三种格式）

### 项目背景

同提示词 1 的"项目背景"。补充：

- 主区域 1（`#results`）：带差异颜色标注的对比结果视图（左右两栏，即"修整后文字"两侧）
- 主区域 3（`.pdf-panels`）：`带差异颜色标注的对比`原始文件渲染区（左右两个面板，PDF 为 canvas 渲染）
- 导出涉及的 4 个区块 = 区域 1 的左/右两栏 + 区域 3 的左/右两面板的当前视觉快照
- 批量对比为规划中的能力（见 worklist.md）：选定对比源文件夹后批量执行多对文件的对比。本功能服务于批量场景，但格式 ① 也适用于单次对比

### 需求

实现对比结果的导出，共两种产物：**① 单对自包含 HTML 报告；② 批量合并 HTML 报告（内含"左右分栏 / Redline 合并"双视图切换）**。**共同要求：自包含单文件，接收方零安装双击即看；包含带差异颜色标注的对比文字 + 原始文件的视觉快照（`带差异颜色标注的对比`，canvas 导出为图片内嵌）。**

#### 格式 ①：单对自包含 HTML 报告

- 一次对比导出为一个 .html：头部为摘要（文件名、对比时间、差异统计：新增/删除/修改各多少处），主体为 4 区块内容
- 保留只读交互：折叠/展开相同行、上一处/下一处差异跳转；所有 CSS/JS/图片内嵌，不依赖外部文件
- 本质是把当前页面的对比结果"冻结"为静态文件

#### 格式 ②③：批量合并 HTML 报告（分栏 / Redline 双视图切换，已确定合并为一个 HTML）

- 批量对比的全部结果放入**同一个** .html：
  - 开头是**总览**：每对文件一行（文件名、差异数、若提示词 3 已落地则附语义影响结论），每行是锚点超链接
  - 正文是各对文件的完整报告，按总览顺序排列，点击总览行跳转定位
- 每对文件的正文提供**两种视图，报告内一键切换**（数据同源，只是渲染不同）：
  - **左右分栏视图**：结构同格式 ①，带差异颜色标注的左右两栏 + 原始文件快照
  - **Redline 合并视图**：合并成一份文档，删除的内容用红色删除线、新增的内容用蓝色下划线，未变内容正常黑色——一份文件看完全部差异（法律行业 redline 风格）
  - 两种视图都离线可用（切换逻辑 JS 内嵌在报告里），记住用户上次选择的视图（报告内 localStorage 或默认分栏即可，不强制）
- 注意体积控制：原始文件快照图片按需压缩（降低分辨率/质量），并在批量数量大时给出导出耗时与体积预估提示

### 约束

- 纯前端实现：HTML 用字符串模板/DOM 序列化生成，图片用 canvas `toDataURL`；不引入服务端、不引入构建工具
- 模板与导出逻辑独立成模块文件（如 `src/report.js`），样式内联在模板中，与页面运行时样式解耦（避免页面样式改动破坏已导出报告）
- 遵循项目 CLAUDE.md：最小改动、不重构无关代码

### 验收标准

- 格式 ①：导出后在未安装本应用的电脑上双击打开，4 区块内容与颜色标注完整，折叠/差异跳转可用
- 格式 ②③：批量 10 对文件导出一个 HTML，总览 10 行、点击可跳转；Redline 视图增删颜色正确（红删除线/蓝下划线）、分栏与合并视图可离线切换
- **体积标准（已修订）**：快照清晰度优先，**不设单对体积上限**，不得为压体积而降低截图分辨率；改为按"一份报告最多 10 对"控制单份规模，超出由调用方分卷成多份报告（见提示词 4）

## 提示词 4：无头渲染通道（自动生成对比报告，供插件调用）

> 与提示词 3 的关系：**报告模板 `src/report.js` 两者共用**。提示词 3 是"人在页面里点导出"，本提示词是"无人工介入自动生成"。
> 建议先落地本提示词的第 1、2、3 项（管线解耦 + 无头通道），报告模板可先只做"分栏视图"跑通闭环，Redline 与批量总览随后补。

### 项目背景

同提示词 1 的"项目背景"。补充与本功能直接相关的事实：

- 主区域 1（`#results`）：带差异颜色标注的文字对比结果（左右两栏）

### 需求

让应用能在**无任何人工交互**的情况下完成一对或一批文件的对比，并产出**自包含 HTML 报告**（含带颜色标注的文字差异 + 原始文件的**视觉快照**），供 deepseek harness 插件调用（见提示词 5）。

##### 已知的坑（务必逐条处理）

1. **负/零高度的 clip 会让 `Page.captureScreenshot` 永久挂起**（不是报错，是静默卡死）。
   若目标页不在滚动视口内，`bot-top` 会算出负数，调用随即挂死。
   → 截图前必须校验 `clipH > 0`，且**给每个 CDP 调用加超时**，超时即失败而非卡住整批。
2. **截图前必须解除协同滚动绑定，并把重绑也掐死。**
   应用在布局变化时会调用 `SyncScroll.rebind(...)` 重新绑定。只调一次 `SyncScroll.rebind([])` 不够——实测部分页面的 `scrollTop` 会在 200ms 内被拉回 0，导致该页落在视口外。
   → 无头模式下：先 `SyncScroll.rebind([])`，再 `SyncScroll.rebind = function(){}`。
3. **`scrollTop` 要"写到稳定"，不能写一次就走。**
   → 循环：写 `scrollTop` → 等待 → 校验读回值 → 再观察一次确认没被拉回；不稳定就重试。
   → **末页的目标值会超过滚动上限**，必须 `Math.min(目标, scrollHeight - clientHeight)`，否则永远判定为"没收敛"，白白重试多轮。
4. **默认布局下 PDF 面板只有约 186px 高**，一页都放不下。
   原因：`.pdfarea` 有 `max-height: 65vh`，且被上方的主区域 1/2 挤压。
   → 无头模式注入样式：隐藏主区域 1/2 与两条拖拽条、`.pdfarea` 覆盖 `max-height:none` 并允许撑满，使面板高度足以容纳一整页（实测 1146px vs 页高 792px）。
5. **性能**：实测约 **815ms/页**（含滚动收敛等待）。100 页的文档约 80 秒。批量场景要显示进度，并考虑把等待时间调优（当前收敛等待偏保守）。
6. **协同滚动被解除后，PDF 面板与主区域 1 的行号锚定关系在截图期间不再维持**——这对截图无影响（我们只截面板），但说明无头模式下的面板状态与交互态不同，不要依赖界面上的滚动联动。

#### 5. 报告模板（`src/report.js`）

- **自包含单文件**：CSS / JS / 图片（base64 内嵌）全部内联，接收方零安装双击即看

- **批量报告**：**一份报告最多 10 对**，超出由调用方分卷成多份（本模块不自行分卷）。开头为总览（每对一行：文件名、差异数、锚点超链接），正文按总览顺序排列
- 每对提供两种视图、报告内一键切换：**左右分栏** / **Redline 合并**（删除=红色删除线、新增=蓝色下划线）

- 模板与页面运行时样式**解耦**（页面改样式不得破坏已导出的报告）

## 提示词 5：deepseek harness（dsh）插件对接

### 项目背景

同提示词 4。落地本提示词的前提是：应用已能通过 `node tools/render.js --task task.json` 无头产出对比报告。

### 需求

让 dsh 能通过**自然语言对话**驱动本应用完成对比并产出报告：用户用一句话描述要比什么、怎么比，dsh 产出报告。

### 具体要求

1. **插件形态**：优先使用 harness 原生的**自定义命令 / skill**（一份描述文件 + 一次命令调用），**不引入常驻后台服务**。若 harness 支持 MCP，可再包一层极薄的 MCP server，内部复用同一个 CLI，不重复实现逻辑。
2. **自然语言 → 任务 JSON 由 harness 的 LLM 完成**。插件侧只提供**任务 JSON 的 schema 说明 + 若干范例**（写进 skill 描述文件），**不要自己写规则解析**（正则硬抽需求既脆弱又没必要，LLM 就是干这个的）。
3. 必须能被自然语言表达的需求：
   - 指定对比源文件夹 + 通配/名单，自动成对（原始=第一个 / 修改=第二个，或按文件名规则配对）
   - 六个忽略选项（大小写 / CRLF / 空格 / 换行 / 全半角 / 标点）
   - 输出路径与报告标题
4. **分卷**：一份报告最多 10 对。**超过 10 对时由插件自动切成多份报告**，并把全部报告路径返回给用户。
5. **调用协议**：插件只与 `tools/render.js` 的标准输出 / 退出码交互；错误必须结构化（JSON）且退出码非 0，便于 dsh 理解并向用户解释。
6. **语义分析不在应用内实现**（这是提示词 2 的替代）：报告产出后，由 dsh 直接阅读报告中的差异统计与差异片段做语义判断。**应用侧不配置任何大模型 API、不管理 API Key。**

### 约束

- 应用本体不得因此新增常驻进程或后台服务
- 插件层代码保持轻薄（目标 < 500 行），复杂逻辑一律留在应用侧
- 不得将报告内容或任务信息上传到任何网络地址

### 验收标准

- 对话说"把 `D:\a` 和 `D:\b` 下的合同按文件名两两对比，忽略大小写和空格，出一份报告"，dsh 能产出正确的任务 JSON 并成功调用，用户拿到可打开的报告
- 一次 25 对文件的需求：自动分成 3 份报告（10/10/5）并返回全部路径
- 未安装 Edge / 路径不存在 / 输入非法时：dsh 能拿到结构化错误并向用户说明原因，应用不崩溃
