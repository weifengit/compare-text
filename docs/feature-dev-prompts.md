## 提示词 1：扫描版 PDF 的 OCR 识别（连接本机 PaddleOCR 环境）

### 项目背景

这是一个 Tauri 2 + 纯前端（无框架，原生 JS）的离线文本对比工具。仓库结构：

- 前端入口 `index.html`，逻辑在 `src/` 下按模块拆分（`app.js`、`pdfview.js`、`compute.js` 等）
- PDF 渲染与文本提取用 pdf.js（`lib/pdf.min.js`），文本提取在 `src/pdfview.js` 的 `extractText`（基于 `getTextContent`，**只能提取文字版 PDF，扫描件提取结果为空**）
- Rust 后端在 `src-tauri/`，目前很薄（仅 log、open 插件），可以通过 `tauri::command` 扩展
- 当前 CSP（`src-tauri/tauri.conf.json`）：`connect-src 'self' blob: ipc:`

### 需求

为扫描版（无文字层）PDF 增加 OCR 识别能力，使这类文件也能参与文本对比。

**已选定的技术路线：应用不内置 OCR，连接用户本机已安装好的 PaddleOCR 环境。** 用户已按官方方式安装：`uv add "paddleocr[doc-parser]"`（含表格识别等高级能力）。

### 具体要求

1. **环境检测与配置**

   - 应用启动时（或首次需要 OCR 时）自动检测本机可用的 PaddleOCR 环境：尝试常见的 uv venv 路径、`which python`/`python3` 并验证 `import paddleocr` 可用
   - 设置界面中允许用户手动指定 Python 解释器路径（或 uv 项目目录），并做有效性验证（实际跑一条 `python -c "import paddleocr; print(paddleocr.__version__)"`）
   - 检测不到环境时给出明确引导文案（如何安装），不要静默失败
2. **调用方式（已确定：常驻本地 HTTP 服务）**

   - 通过 Rust 端 `tauri::command` 拉起 Python 子进程，启动一个**常驻本地 HTTP 服务**封装 PaddleOCR（模型只加载一次，避免每次对比都冷启动数秒~十几秒）
   - 服务要求：端口随机分配（启动时探测空闲端口）、仅监听 127.0.0.1、应用退出时可靠回收子进程（含异常退出路径，避免残留孤儿进程）；服务异常崩溃后下次请求时自动重启
   - 接口约定：输入 PDF 文件路径 + 页码范围；输出结构化 JSON（每页的文本行及置信度，**保留版面顺序**）
   - OCR 在服务进程中执行，超时与取消机制必须有（大文件 OCR 可能数分钟），UI 上显示进度并允许取消（取消时终止服务侧当前任务）
3. **与对比流程的集成**

   - 加载 PDF 时先走现有 `extractText`，若提取结果为空/极少（判定为扫描件），在主区域3（原始文件显示区)显著提示"该 PDF 无文字层，是否启用 OCR 识别？"，用户确认后才启动 OCR，**不要默认自动跑**
   - OCR 结果作为该侧文本进入现有对比流程，与文字版 PDF 的行为完全一致
   - OCR 结果按文件缓存（文件内容 hash 为 key），同一文件二次打开直接读缓存
4. **暂不做**：生成带文字层的可搜索 PDF（可作为后续迭代，本次只产出对比用纯文本）；表格结构识别结果的可视化（doc-parser 能力先透传保留字段即可）

### 约束

- 应用本体打包体积不得因此功能明显增加（Python 环境完全由用户自备，不打包任何模型/解释器）
- 保持离线：OCR 全程本地，不允许引入任何网络请求
- 遵循项目 CLAUDE.md：最小改动、匹配现有代码风格、功能模块化（OCR 相关逻辑独立成新文件，不堆进 `pdfview.js`）

### 验收标准

- 未装 PaddleOCR 的机器：功能入口给出安装引导，应用其他功能不受影响
- 装有 PaddleOCR 的机器：打开一份扫描版 PDF，确认后 OCR 出的文本进入对比，差异标注正常；同一文件第二次打开秒开（走缓存）
- OCR 进行中可取消，取消后应用状态干净（无残留子进程）

## 提示词 2：Word 文档（.docx）识别与展示

### 项目背景

同提示词 1 的"项目背景"。补充：主区域 3（`index.html` 中 `#pdfarea` > `.pdf-panels` 的 `#pdfLeft`/`#pdfRight`）目前只渲染 PDF（pdf.js canvas），文件选择逻辑在 `src/pdfview.js` 与 `src/app.js`。

### 需求

支持打开 `.docx` 文件：提取其文本进入对比流程，并在主区域 3 中原样呈现文档内容。

**已选定的技术路线：`docx-preview` + `mammoth.js` 组合。**

- **mammoth.js**：负责从 docx 提取纯文本（供对比使用）
- **docx-preview**：负责把 docx 渲染为 HTML（供主区域 3 展示，保真度优于 mammoth 的 HTML 转换）

### 具体要求

1. 文件打开入口接受 `.docx`（与 PDF 同一入口，按扩展名/文件头分流）；`.docx` 是 zip，可用文件头 `PK\x03\x04` 辅助判断
2. 文本提取：mammoth.js `extractRawText`，结果接入现有对比流程，与 PDF/纯文本行为一致
3. 展示：docx-preview 渲染到主区域 3 对应侧的面板中；该面板需兼容"PDF 页"与"docx HTML"两种内容形态（缩放、同步滚动等现有交互在 docx 模式下合理降级即可，不要求完全一致）
4. 旧格式 `.doc`（二进制）：**不支持**，选择时明确提示"请先用 Word/WPS 另存为 .docx"，不要静默失败或显示乱码
5. 两个库走本地化引入（放入 `lib/`，与 pdf.js 同方式），不引入 CDN、不引入构建工具链（项目目前是无打包器的纯静态结构，保持这一点；选库时用与浏览器 script 标签直接兼容的构建产物）

### 约束

- 两个库合计体积控制在 ~500KB 级别，不得引入大型依赖
- 保持离线，CSP 不需要为此改动
- 遵循项目 CLAUDE.md：最小改动、docx 相关逻辑独立成模块文件

### 验收标准

- 打开一份含标题、表格、图片的常见 docx：文本正常进入对比、主区域 3 渲染版式基本正确
- docx 与 PDF、docx 与 docx、docx 与粘贴文本均可互相对比
- 选择 .doc 文件时给出明确提示

## 提示词 3：文本差异语义识别（云端大模型 API）

### 项目背景

同提示词 1 的"项目背景"。补充：差异计算在前端 `src/compute.js` 完成（基于 `lib/diff.min.js`），产出结构化的行级差异（新增/删除/修改），UI 上有"折叠相同行""仅看差异"等过滤能力（`src/filterbar.js`）。

### 需求

在现有字符级差异的基础上，增加**语义级分析**：判断这批文字差异对文档上下文语义的影响程度，给出"影响大 / 中 / 小"的结论与简要理由。

**已选定的技术路线：调用云端大模型 API，用户自行配置厂商与 API Key。** 不引入本地模型。

### 具体要求

1. **配置**

   - 设置界面：API Base URL、API Key、模型名，默认兼容 OpenAI 格式的 `/chat/completions`（这样 OpenAI、DeepSeek、通义、Kimi 等主流厂商都能接）；Key 本地安全存储（Tauri 侧存系统 keychain 或至少不明文落盘到仓库目录），永不回传除用户所配厂商之外的任何地址
   - 提供"测试连接"按钮验证配置可用
2. **分析流程**

   - 输入：从现有差异结果中提取**差异片段 + 必要的上下文窗口**（差异前后各若干行），不是整篇文档无脑发送；差异很多时分批/汇总，控制 token 消耗
   - 输出（要求模型返回结构化 JSON，程序解析而非展示原始文本）：整体影响等级（大/中/小）、一句话结论、以及逐处差异的简要说明（可选，按 token 预算取舍）
   - 结果展示在差异区域顶部/侧边，与现有 UI 风格一致
3. **隐私与降级**

   - 首次使用该功能时明确提示：差异内容将发送至用户配置的第三方 API
   - 未配置 API、网络失败、额度不足时，应用其他功能完全不受影响，该功能单独给出错误提示
4. **CSP 调整**：`tauri.conf.json` 的 `connect-src` 需放开到允许用户配置的 API 域名（实现时评估：按用户配置动态注入，或放宽为 `https:` 并在文档中说明安全影响）

### 约束

- 不引入前端框架/重型 SDK，直接 `fetch` 调 OpenAI 兼容接口
- 除该功能外应用保持离线可用
- 遵循项目 CLAUDE.md：最小改动、LLM 调用与结果渲染逻辑独立成模块文件

### 验收标准

- 配置有效 Key 后：对一份有实质语义变化（如合同金额、责任条款改动）的对比，结论判"影响大"并给出理由；对仅措辞微调的对比，判"影响小"
- 未配置/断网时：功能入口提示明确，其余功能正常

## 提示词 4：批量对比结果导出（三种格式）

### 项目背景

同提示词 1 的"项目背景"。补充：

- 主区域 1（`#results`）：带差异颜色标注的对比结果视图（左右两栏，即"修整后文字"两侧）
- 主区域 3（`.pdf-panels`）：原始文件渲染区（左右两个面板，PDF 为 canvas 渲染）
- 导出涉及的 4 个区块 = 区域 1 的左/右两栏 + 区域 3 的左/右两面板的当前视觉快照
- 批量对比为规划中的能力（见 worklist.md）：选定对比源文件夹后批量执行多对文件的对比。本功能服务于批量场景，但格式 ① 也适用于单次对比

### 需求

实现对比结果的导出，共两种产物：**① 单对自包含 HTML 报告；② 批量合并 HTML 报告（内含"左右分栏 / Redline 合并"双视图切换）**。**共同要求：自包含单文件，接收方零安装双击即看；包含带差异颜色标注的对比文字 + 原始文件的视觉快照（canvas 导出为图片内嵌）。**

#### 格式 ①：单对自包含 HTML 报告

- 一次对比导出为一个 .html：头部为摘要（文件名、对比时间、差异统计：新增/删除/修改各多少处），主体为 4 区块内容
- 保留只读交互：折叠/展开相同行、上一处/下一处差异跳转；所有 CSS/JS/图片内嵌，不依赖外部文件
- 本质是把当前页面的对比结果"冻结"为静态文件

#### 格式 ②③：批量合并 HTML 报告（分栏 / Redline 双视图切换，已确定合并为一个 HTML）

- 批量对比的全部结果放入**同一个** .html：
  - 开头是**总览**：每对文件一行（文件名、差异数、若提示词 3 已落地则附语义影响结论），每行是锚点超链接
  - 正文是各对文件的完整报告，按总览顺序排列，点击总览行跳转定位
- 每对文件的正文提供**两种视图，报告内一键切换**（数据同源，只是渲染不同）：
  - **左右分栏视图**：结构同格式 ①，带差异颜色标注的左右两栏 + 原始文件快照
  - **Redline 合并视图**：合并成一份文档，删除的内容用红色删除线、新增的内容用蓝色下划线，未变内容正常黑色——一份文件看完全部差异（法律行业 redline 风格）
  - 两种视图都离线可用（切换逻辑 JS 内嵌在报告里），记住用户上次选择的视图（报告内 localStorage 或默认分栏即可，不强制）
- 注意体积控制：原始文件快照图片按需压缩（降低分辨率/质量），并在批量数量大时给出导出耗时与体积预估提示

### 约束

- 纯前端实现：HTML 用字符串模板/DOM 序列化生成，图片用 canvas `toDataURL`；不引入服务端、不引入构建工具
- 模板与导出逻辑独立成模块文件（如 `src/report.js`），样式内联在模板中，与页面运行时样式解耦（避免页面样式改动破坏已导出报告）
- 遵循项目 CLAUDE.md：最小改动、不重构无关代码

### 验收标准

- 格式 ①：导出后在未安装本应用的电脑上双击打开，4 区块内容与颜色标注完整，折叠/差异跳转可用
- 格式 ②③：批量 10 对文件导出一个 HTML，总览 10 行、点击可跳转；Redline 视图增删颜色正确（红删除线/蓝下划线）、分栏与合并视图可离线切换；文件体积合理（快照压缩后单对增量 < 1MB 量级）
